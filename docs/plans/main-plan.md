# Omni-Path 100 performance plan

## Current state (2026-08-09)

- Both HFI ports are `ACTIVE` at 100 Gb/s over 4 lanes (sysfs prints the IB-compat string `4X EDR`) and both PCIe links are Gen3 x16. T7610's `opa-fm` is MASTER.
- **PSM2 now works end to end.** `psm2_ep_open()` succeeds on both hosts and MPI over the PSM2 MTL transfers data across the fabric. This required fixing three independent defects.
- Defect 1, kernel: `hfi1_file_mmap()`'s PIO_CRED case was wrong in three ways at once — it indexed the credit-return buffer by `uctxt->numa_id` instead of the send context's own node, added a byte offset to a `struct credit_return *` (scaling it by 64), and offset `cpu_addr` instead of using `vma->vm_pgoff`, which `dma_mmap_coherent()` requires. The first caused `-ENXIO`, the second the `Corrupted page table` Oops, the third a silent wrong-page mapping that hung every send-PIO transfer. Fixed by [one patch](../../patches/hfi1-pio-cred-mmap-fix-v6.17.patch); upstream v6.17 carries the same code.
- Defect 2, userspace: `opa-psm2` compiles the whole library with `-mavx2` by default, and T7610's Xeon E5-2650 v2 has no AVX2, so both the Ubuntu package and any default local build `SIGILL` during context open. Rebuilt with `PSM_DISABLE_AVX2=1` and installed in `/usr/local/lib` on T7610. WRX80 is unaffected.
- Defect 3, packaging: T7610's `rdma-core` renamed the device to `opap129s0` via `rdma_rename %k NAME_FALLBACK`, which breaks PSM2's fixed `hfi1_<unit>` sysfs discovery (`psm2_init` err=8). A local udev override pins `NAME_KERNEL`. The old process-local `HFI_SYSFS_PATH` alias workaround is retired.
- **Sustained bandwidth**: PSM2 reaches **95.5 Gb/s WRX80->T7610** (4 processes per host) and **92.9 Gb/s T7610->WRX80** (8 processes). Both are close to the 96.97 Gb/s that 100 Gb/s of signalling yields after 64b/66b encoding, i.e. practical line rate. Transfers were verified against the HFI `TxWords`/`RxWords` counters.
- **TID RDMA (Accelerated RDMA) is enabled** for kernel Verbs RC QPs via `cap_mask=0x4c09a09cbba` in `/etc/modprobe.d/hfi1-tid-rdma.conf` on both hosts (driver default plus `HFI1_CAP_TID_RDMA` bit 5 and `HFI1_CAP_OPFN` bit 16). Bit 5 is load-time only, so it needs a module reload; `tools/hfi1-typefix-activate --reload` does that while keeping the PIO_CRED fix. Both RDMA Write and RDMA Read gain from it: with the data direction held at WRX80->T7610 and 4 QPs, Write goes 50.0 -> 71.5 Gb/s (+43%) and Read 48.3 -> 72.3 Gb/s (+49%), each confirmed by a full A/B. Tracing confirms the TID path is taken for Read (`hfi1_rsp_rcv_tid_read_req` on the responder). No NAKs, resends or timeouts under load.
- TID RDMA does not affect PSM2, as the source implies (it is gated on `IB_QPT_RC`): an A/B measured 92.7-92.9 Gb/s either way.
- **Verbs needs eight QPs, not four.** Four was inherited from the original baseline and is too few. At eight: Write 88.6 and Read 87.6 Gb/s WRX80->T7610, Write 76.5 and Read 73.3 Gb/s in reverse. Sixteen and thirty-two QPs are no better. Read and Write agree within a few percent once the data direction is matched, so there is no read/write asymmetry — only the directional one.
- Three tuning steps mattered: the `performance` CPU governor (T7610 sat at 1200 MHz of 3400 under `schedutil`, which cost roughly half the bandwidth when it sends), pinning each rank to its own HFI-local physical core, and measuring over ~165 GiB per run instead of a few seconds.
- The apparent run-to-run variance was a measurement artefact of short runs, not a fabric or driver problem: at ~165 GiB per run the same configuration repeats to within a fraction of a percent. `PSM2_SHAREDCONTEXTS`, `PSM2_MTU`, `PSM2_MQ_RNDV_HFI_WINDOW`, hfi1 interrupt placement and idle gaps all made no difference once the measurement was sound.
- **PSM2 is at the wire limit.** 95.3 Gb/s at 4 pairs; 6, 8, 12 and 16 pairs all measure lower. After OPA's 1024-in-1056-bit LTP framing (96.97%, specification) and the 0.95% packet-header overhead measured from the HFI counters, payload capacity is about 96.0 Gb/s, so 95.3 is roughly 99% of it.
- **Why T7610 is slower as a Verbs sender (75-76 versus 88-89 Gb/s), with evidence.** Not the hardware — the same host sends 92.6 Gb/s over PSM2. Not aggregate CPU — Verbs costs 6.93 cores per 100 Gb/s against PSM2's 8.01, with only 5.22 of 32 CPUs busy. Not the SDMA engines — `DmaWait` was 5,016 on T7610 at 75.5 Gb/s against 103,947 on WRX80 at 88.3 Gb/s, so T7610 never reaches SDMA back-pressure. Not the arrangement — 4/8/16/32 QPs, 1/2/4 processes, clean versus IRQ-loaded cores, and separate SLs all plateau at 75-76 (SLs are worse). What differs is the CPU-side kernel Verbs send path: engine load is skewed 3:1.5:1 because `sdma_select_engine_sc()` picks by a QP-number hash with no load feedback (`qp.c:552`, `sdma.c:765`), against PSM2's even 1% spread, and Verbs raises 2.4x as many SDMA interrupts per byte. T7610's 2.6 GHz Ivy Bridge cores execute that work more slowly.
- The earlier suspicion that the AVX2-free PSM2 build caused the asymmetry is refuted: WRX80 running the same AVX2-free library measured 20.03/19.06 Gb/s per process against 19.33/18.85 with the distribution AVX2 build.
- The patched `hfi1` is installed on both hosts as `/lib/modules/<version>/updates/hfi1.ko`, which takes precedence over the packaged module without modifying it, so the fix now survives a reboot. `tools/hfi1-typefix-activate` provides `--status`, `--rehearse`, `--activate`, `--restore`, `--install-persistent` and `--uninstall-persistent`. `tools/cpu-performance-governor.service` is installed and enabled on both hosts, so the governor is restored on boot as well.

## Decision and unresolved work

- The 90 Gb/s target is exceeded: 95.5 Gb/s sustained WRX80->T7610 over PSM2, and 92.9 Gb/s in reverse. The earlier conclusion that improvement was exhausted at ~66 Gb/s applied only to direct Verbs with a broken PSM2 stack and TID RDMA disabled.
